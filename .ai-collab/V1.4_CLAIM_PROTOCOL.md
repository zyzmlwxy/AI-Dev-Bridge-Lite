# AI Dev Bridge Lite V1.4 — Claim Protocol and Executor State Machine

Status: **Design proposal; not an execution authorization**

This document specifies a reusable, GitHub-backed task claim protocol for the ChatGPT (design/code/review) + WorkBuddy (local execution) workflow. It builds on the V1.3 handoff/evidence rules and the October 2026 PR #16 claim-ref experiment.

## 1. Goals and non-goals

### Goals

- Identify a task by an immutable source revision, not by a moving branch name.
- Allow only explicitly opted-in, allowlisted same-repository PRs to enter the queue.
- Make the first valid claim discoverable and cause compliant later pollers to skip it.
- Handle ambiguous network results by reading remote state before taking further action.
- Preserve an auditable history without rewriting the claim record.
- Fail closed on stale revisions, malformed records, missing permissions, unknown state, or incomplete evidence.

### Non-goals

- This is not a distributed lock service or a security boundary against a compromised executor with the same Git credentials.
- It does not automatically invoke ChatGPT, grant a PR authority to run arbitrary shell commands, merge, release, or deploy.
- It does not authorize production execution. Execution stays disabled until a project configuration and a separate execution-stage approval exist.

## 2. Sources of truth and task identity

For each configured repository, the poller must load the repository's root `AGENTS.md`, project configuration if present, project status if present, and current PR metadata. Missing configuration fields are `UNKNOWN`, never guessed.

A candidate is eligible only when every configured rule passes:

1. Repository is explicitly allowlisted in the executor configuration.
2. PR is in the same repository (no fork head), open, and not a draft.
3. Base branch matches the configured stable/integration branch.
4. The explicit opt-in label `ai-bridge:execute` is present.
5. The full 40-character HEAD SHA is available and unchanged across the pre-claim re-read.
6. The requested task and allowed commands are within the project's approved scope.
7. No policy, permission, or evidence check returns `UNKNOWN` or `BLOCKED`.

The deterministic run key is:

```text
<owner>/<repo>#<PR-number>@<full-40-char-head-sha>
```

Example:

```text
zyzmlwxy/AI-Dev-Bridge-Lite#16@a3c9044f01777279274aaa4c302ebf6ff1b6b89e
```

The key intentionally changes when the PR HEAD changes. A changed HEAD is a new candidate revision and must pass all checks again. The previous revision's claim never authorizes the new revision.

## 3. Deterministic claim ref and immutable claim record

Use a deterministic branch ref derived from repository-local PR number and full HEAD SHA:

```text
refs/heads/ai-bridge/claims/pr-<number>-<full-head-sha>
```

The first claim commit must be based **directly on the exact PR HEAD SHA** and add exactly one new file:

```text
.ai-collab/claims/pr-<number>-<full-head-sha>.json
```

The initial record contains:

- `schema_version`
- `state: CLAIMED`
- `run_key`
- `repository`
- `pr_number`
- `head_sha`
- `claim_ref`
- `claimed_at_utc` (set once; never refreshed)
- `claim_attempt_id` (unique per contender)

The record must be valid UTF-8 JSON, contain no credentials, and exactly match the ref, PR number, repository, and full HEAD SHA. Before pushing, verify the candidate commit has exactly one parent equal to the target PR HEAD and the only changed path is the claim record. Use a repository-local Git identity/config only.

**Never modify the initial claim JSON or its timestamp after the first claim.** Later state changes, if required, are append-only event files on the claim ref; each event is a new file/commit, and no existing event is edited or removed. Each transition commit must be based on the currently observed remote tip. A non-fast-forward rejection requires a remote re-read and state-machine re-evaluation, never force-push or blind retry.

## 4. First-writer claim algorithm

1. Read PR metadata and validate eligibility. Capture the full HEAD SHA.
2. Read PR metadata again immediately before claim creation. If state, draft flag, base, label, repository identity, or HEAD differs, return `BLOCKED` or `STALE`; do not write.
3. Query the deterministic claim ref with `git ls-remote` or an equivalent authorized Git read.
4. If the ref exists:
   - Fetch/read its claim record.
   - If the record is valid and its `run_key`, repository, PR number and `head_sha` exactly match the candidate, return `DUPLICATE_SKIP`; do not execute or create another claim.
   - If the record is missing, malformed, mismatched, or inconsistent with the ref history, return `BLOCKED` and request manual reconciliation.
5. If the ref does not exist, create one candidate claim commit directly on the exact PR HEAD. Do not reuse a dirty/stale local branch. Verify the parent and changed-path invariants.
6. Push only the deterministic claim ref using an ordinary non-force push. Never push the PR branch or stable branch as part of claiming.
7. Re-read the remote ref and record after the push:
   - Remote ref equals this candidate commit and `claim_attempt_id` matches this invocation: claim confirmed; return `CLAIMED`.
   - A valid matching run key exists but the attempt ID differs: another contender won; return `DUPLICATE_SKIP`.
   - Remote state is malformed or refers to another task/revision: `BLOCKED`.
   - Push outcome is ambiguous and remote state cannot yet be confirmed: `UNKNOWN`; do not start execution. Poll/read later for reconciliation; do not blindly create a new candidate.
8. If the server rejects a divergent push as non-fast-forward, re-read the winning ref. Only a valid matching record proves `DUPLICATE_SKIP`; otherwise return `BLOCKED`.

The Git server's ref-update checks provide a useful first-writer primitive for compliant contenders that create divergent commits from the same PR HEAD and push to the same deterministic ref. The PR #16 test verified a sequential divergent update was rejected. **A truly simultaneous create-ref race has not yet been tested.** Do not claim full concurrency safety until that test passes.

## 5. Execution state machine

Separate queue discovery results from durable execution states.

### Discovery/claim outcomes

- `NO_TASK`: no eligible opted-in PR exists.
- `TASK_FOUND`: eligible PR metadata has been identified; no execution permission is implied.
- `CLAIMED`: this invocation's claim ref and record were confirmed remotely.
- `DUPLICATE_SKIP`: a valid claim for the same run key already exists, or another contender won.
- `STALE`: the PR HEAD or eligibility changed during preflight.
- `BLOCKED`: permissions, policy, record validation, or required configuration failed.
- `UNKNOWN`: a remote write may have succeeded but cannot be confirmed. No execution is allowed.

### Execution states (future stage; disabled by default)

```text
UNSEEN
  -> VALIDATING
      -> NO_TASK
      -> BLOCKED
      -> STALE
      -> TASK_FOUND
          -> CLAIMING
              -> CLAIMED
              -> DUPLICATE_SKIP
              -> BLOCKED
              -> UNKNOWN
                  -> RECONCILING (read-only)
                      -> CLAIMED / DUPLICATE_SKIP / BLOCKED
              -> CLAIMED
                  -> RUNNING
                      -> REPORT_PENDING
                          -> COMPLETED
                          -> FAILED
                          -> BLOCKED
                      -> FAILED
                      -> BLOCKED
                      -> RECOVERY_REQUIRED
```

Terminal outcomes for a given run key are `COMPLETED`, `FAILED`, `BLOCKED`, `STALE`, and `RECOVERY_REQUIRED`. No automatic retry or reclaim is allowed after an ambiguous, failed, or abandoned run in this version. A retry requires explicit policy/owner approval and a separately recorded attempt; never delete or overwrite the original claim.

### Transition rules

| Current state | Allowed next state | Guard |
|---|---|---|
| `UNSEEN` | `VALIDATING` | Poller started with repository allowlist |
| `VALIDATING` | `NO_TASK` | No eligible PR |
| `VALIDATING` | `TASK_FOUND` | All discovery predicates pass |
| `VALIDATING` | `BLOCKED` / `STALE` | Policy/config/metadata failure or moving HEAD |
| `TASK_FOUND` | `CLAIMING` | Pre-claim re-read still matches |
| `CLAIMING` | `CLAIMED` | Remote ref and own attempt ID verified |
| `CLAIMING` | `DUPLICATE_SKIP` | Existing/winning valid claim matches run key |
| `CLAIMING` | `UNKNOWN` | Write outcome cannot be confirmed |
| `CLAIMING` | `BLOCKED` | Invalid record, permission error, or conflicting task |
| `UNKNOWN` | `RECONCILING` | Read-only remote inspection only |
| `RECONCILING` | `CLAIMED` / `DUPLICATE_SKIP` / `BLOCKED` | Determined from remote truth; never from assumption |
| `CLAIMED` | `RUNNING` | Only after a later stage is explicitly enabled and pre-execution SHA/policy checks pass |
| `RUNNING` | `REPORT_PENDING` | Approved command set completed and report assembled |
| `REPORT_PENDING` | `COMPLETED` | Evidence is committed and validated against tested SHA |
| `RUNNING` / `REPORT_PENDING` | `FAILED` / `BLOCKED` | Actual execution or policy failure |
| `RUNNING` | `RECOVERY_REQUIRED` | Timeout/crash/unknown side effects; human reconciliation required |

A poller must not turn `TASK_FOUND` directly into `RUNNING`. Claim verification and a separate execution authorization are mandatory.

## 6. Abandoned claims, stale SHA, and retry policy

- If the PR closes, becomes a draft, loses its opt-in label, changes base, or its HEAD changes before execution, do not execute. Mark the candidate stale/blocked in the run evidence; never transfer the old claim to the new SHA.
- If a worker crashes after claiming or the execution result is unknown, preserve the claim and require manual reconciliation. Do not infer that a timeout means the command did not run.
- This version has no automatic lease expiration or claim stealing. Expiring a claim based only on wall-clock time can create two executors if the original worker is merely slow/offline.
- A retry after a terminal failure requires an explicit owner-approved retry policy and a distinct attempt identity with auditable linkage to the original run. Never reset the original claim in place.
- The claim ref and all audit records are retained until a separately approved cleanup procedure exists.

## 7. Execution authorization and safe command boundary

Even a valid claim does not authorize arbitrary code execution.

Before execution is enabled for any repository, its project config must explicitly define:

- allowed repository and stable base branch;
- approved build/test commands and working directory;
- permitted file/system/network scope and timeout;
- expected report path and required evidence;
- whether any write-back is allowed (default: report-only);
- deployment policy (default: `DISABLED`);
- recovery/rollback and human approval requirements.

Commands must come from reviewed project configuration or the approved task contract, not be blindly copied from PR comments, filenames, or untrusted repository text. Fork PRs, arbitrary shell requests, secret exfiltration, force pushes, direct stable-branch writes, merge/release/deploy, and destructive operations are prohibited by default.

Execution must verify the exact claimed HEAD before starting. A report must distinguish the tested SHA from the later report commit SHA, follow the V1.3 evidence contract, and never claim unrun checks passed.

## 8. Concurrency model and known limits

- One scheduled poller is preferred for the MVP; overlapping local runs must be disabled or serialized.
- All claim contenders must use the same deterministic ref and must never force-push.
- Initial claim commits must be divergent children of the same exact PR HEAD; a rejected push must be followed by remote validation.
- The PR #16 experiment tested sequential duplicate reads and a sequential divergent non-fast-forward rejection only. It did not test simultaneous workers, crashes during push, protected-ref policy, or hostile writers sharing credentials.
- GitHub branch refs plus shared SSH credentials are an audit/coordination mechanism, not a cryptographic authorization boundary. If multiple independent executors or adversarial concurrency become requirements, add a separately reviewed atomic coordination service or stronger per-worker permissions rather than claiming the current protocol is a distributed lock.

## 9. Required observability

Every attempt report must include:

- repository, PR, base branch, full source HEAD SHA and deterministic run key;
- claim ref, candidate claim commit SHA, remote ref SHA, and claim attempt ID;
- state transitions with UTC timestamps (append-only; do not mutate earlier events);
- actual Git operations and exit codes, with secrets redacted;
- whether the result was `CLAIMED`, `DUPLICATE_SKIP`, `STALE`, `BLOCKED`, or `UNKNOWN`;
- if execution was authorized: exact command, environment, exit code, tested SHA, report commit SHA and evidence links;
- any uncertainty, stale state, rejected push, or manual recovery required.

## 10. Implementation gate

This is a design document, not permission to execute. Do not enable unattended build/test until:

1. the protocol and acceptance matrix are reviewed and approved;
2. a truly concurrent first-claim race is tested on a disposable fixture;
3. ambiguous push outcomes, stale SHA, invalid records, missing permissions, and abandoned execution are covered;
4. the executor uses an explicit repository/command allowlist and a single-flight guard;
5. report-only write-back is verified against the V1.3 evidence gate;
6. a user explicitly authorizes the first harmless command execution.

No merge, release, or deployment is authorized by this document.

# AI Dev Bridge Lite V1.4 — Claim Protocol and Executor State Machine

Status: **Design proposal; not an execution authorization**

This document specifies a reusable, GitHub-backed task claim protocol for the ChatGPT (design/code/review) + WorkBuddy (local execution) workflow. It builds on the V1.3 handoff/evidence rules and the October 2026 PR #16 claim-ref experiment.

## 1. Goals and non-goals

### Goals

- Identify a task by an immutable source revision, not by a moving branch name.
- Allow only explicitly opted-in, allowlisted same-repository PRs to enter the queue.
- Make the first valid claim discoverable and cause compliant later pollers to skip it.
- Handle ambiguous network results by reading remote state before taking further action.
- Preserve an auditable history without rewriting the claim record.
- Fail closed on stale revisions, malformed records, missing permissions, unknown state, or incomplete evidence.
- Keep task identity and state transitions independent of deployment topology; a single-executor MVP profile must not become a protocol-level restriction.

### Non-goals

- This is not a distributed lock service or a security boundary against a compromised executor with the same Git credentials.
- It does not automatically invoke ChatGPT, grant a PR authority to run arbitrary shell commands, merge, release, or deploy.
- It does not authorize production execution. Execution stays disabled until a project configuration and a separate execution-stage approval exist.
- Multi-executor operation is out of MVP scope, not forbidden by the protocol; it requires additional validation before being enabled.

## 2. Sources of truth and task identity

For each configured repository, the poller must load the repository's root `AGENTS.md`, `.ai-collab/PROJECT_CONFIG.json`, `.ai-collab/PROJECT_CONFIG.md`, `.ai-collab/PROJECT_STATUS.md`, and current PR metadata from the trusted configured base branch. `PROJECT_CONFIG.json` is the authoritative machine-readable policy; the Markdown file is explanatory documentation only. Parse JSON strictly, validate the supported schema version and field types, and fail closed on malformed JSON, unknown safety-critical values, or disagreement with the human-readable policy. Missing configuration fields are `UNKNOWN`, never guessed. Do not coerce values between types or silently ignore misspelled/unknown keys; reject them as invalid configuration. Any schema change requires an explicit schema-version update and corresponding acceptance tests.

**Trust boundary:** execution policy, repository allowlists, permitted commands, timeouts, writable paths, and deployment settings must be read from the trusted configured base branch (or another separately approved policy source), not from the candidate PR HEAD. The authoritative repository policy is `.ai-collab/PROJECT_CONFIG.json`; `.md` configuration prose must never be parsed as an executable policy source. A PR may propose changes to those policy files, but those changes must not authorize their own execution or take effect before review/merge. If the trusted base lacks required configuration or any required value is `UNKNOWN`, code execution is `BLOCKED`.

### Context loss and evidence freshness

ChatGPT and WorkBuddy may lose conversation context independently. Neither side may assume the other retains previous messages, local command history, or undocumented machine setup. At session start, reconstruct the task from current GitHub state: this protocol, `AGENTS.md`, trusted config, status, Issue/PR, full current HEAD, reviews/checks, commit comparison, and latest execution report.

Preserve durable facts with an explicit evidence grade:
- `VERIFIED`: a fresh, inspectable command/result, exit code, timestamp, execution context and tested SHA are available;
- `USER_REPORTED`: the user reported a capability or result, but the current session has not independently verified it;
- `UNKNOWN`: evidence is missing or ambiguous;
- `BLOCKED`: a specific prerequisite failed, with the failure evidence and next diagnostic action recorded.

Context loss is not evidence that a previously available capability has disappeared, and old success is not proof that the capability still works. For previously available access (including NAS SSH), first inspect the last sanitized evidence and retry the existing local alias/authentication path from the intended machine using a bounded, read-only probe. Record the fresh outcome before relying on it. If it fails, diagnose the observed failure; do not automatically regenerate credentials or alter SSH config, PATH, network policy, NAS services, or permissions.

Do not repeat completed work solely because a session restarted. Compare current GitHub diffs, claims, reports and checks first. Store only sanitized, reproducible facts in GitHub; credentials, private keys, private IPs, real usernames, secret local paths and sensitive logs remain outside the repository. A claim, prior report, or `USER_REPORTED` capability must never be upgraded to `VERIFIED` without matching evidence.

A candidate is eligible only when every configured rule passes:

1. Repository is explicitly allowlisted in the executor configuration.
2. PR is in the same repository (no fork head), open, and not a draft.
3. Base branch matches the configured stable/integration branch.
4. The explicit opt-in label `ai-bridge:execute` is present.
5. The full 40-character HEAD SHA is available and unchanged across the pre-claim re-read.
6. The requested task and allowed commands are within the project's approved scope.
7. No policy, permission, or evidence check returns `UNKNOWN` or `BLOCKED`.

The deterministic run key is:

```text
<owner>/<repo>#<PR-number>@<full-40-char-head-sha>
```

Example:

```text
zyzmlwxy/AI-Dev-Bridge-Lite#16@a3c9044f01777279274aaa4c302ebf6ff1b6b89e
```

The key intentionally changes when the source revision being tested changes. In the ordinary case, this is the PR HEAD SHA. A special case exists for trailing report-only commits: see the next subsection. A changed source revision is a new candidate and must pass all checks again; the previous revision's claim never authorizes new code.

### Effective source SHA and report-only commits

A WorkBuddy report committed to the same PR branch advances the literal PR HEAD even though it does not change the tested source. To avoid re-running the same task forever, determine an **effective source SHA** before building the run key:

1. Start at the current PR HEAD and walk backward through trailing commits only while each commit adds one or more correctly named `.ai-collab/reports/PR-<PR>-<tested-short-sha>-a<Attempt>.md` files and changes no other path. Existing files must not be modified or deleted.
2. The first commit before that trailing report-only chain is the effective source SHA. If the current HEAD is not a report-only commit, the effective source SHA is the current HEAD.
3. Validate any report in the trailing chain against the effective source SHA, report filename, required fields and actual commit comparison. If a valid report already exists for this effective source SHA, return `DUPLICATE_SKIP` / hand off as `REVIEW_PENDING`; do not execute the same source revision again.
4. If a trailing report-only commit is malformed, mixed with source/config/test changes, or claims a different tested SHA, return `BLOCKED` / `EVIDENCE_INVALID` for review; do not run commands or guess.
5. If a later code, test, or build-relevant configuration commit appears after an older report, the new current HEAD becomes the effective source SHA and may be considered a new task if the explicit opt-in and all other gates still pass.

The `head_sha` field in a claim record and the SHA portion of `run_key`/claim ref refer to this effective source SHA. The literal current PR HEAD must also be recorded in each poll result when it differs, so the report chain remains auditable.

## 3. Deterministic claim ref and immutable claim record

Use a deterministic branch ref derived from repository-local PR number and full effective source SHA:

```text
refs/heads/ai-bridge/claims/pr-<number>-<full-head-sha>
```

The first claim commit must be based **directly on the exact PR HEAD SHA** and add exactly one new file:

```text
.ai-collab/claims/pr-<number>-<full-head-sha>.json
```

The initial record contains:

- `schema_version`
- `state: CLAIMED`
- `run_key`
- `repository`
- `pr_number`
- `head_sha`
- `claim_ref`
- `claimed_at_utc` (set once; never refreshed)
- `claim_attempt_id` (unique per contender)

The record must be valid UTF-8 JSON, contain no credentials, and exactly match the ref, PR number, repository, and full HEAD SHA. Before pushing, verify the candidate commit has exactly one parent equal to the target PR HEAD and the only changed path is the claim record. Use a repository-local Git identity/config only.

**Never modify the initial claim JSON or its timestamp after the first claim.** Later state changes, if required, are append-only event files on the claim ref; each event is a new file/commit, and no existing event is edited or removed. Each transition commit must be based on the currently observed remote tip. A non-fast-forward rejection requires a remote re-read and state-machine re-evaluation, never force-push or blind retry.

## 4. First-writer claim algorithm

1. Read PR metadata and trusted base-branch policy. Validate eligibility and compute the effective source SHA.
2. Read PR metadata again immediately before claim creation and recompute the effective source SHA. If state, draft flag, base, label, repository identity, or effective source SHA differs, return `BLOCKED` or `STALE`; do not write.
3. Query the deterministic claim ref with `git ls-remote` or an equivalent authorized Git read.
4. If the ref exists:
   - Fetch/read its claim record.
   - If the record is valid and its `run_key`, repository, PR number and `head_sha` exactly match the candidate, return `DUPLICATE_SKIP`; do not execute or create another claim. If no valid execution report/terminal event exists for this claim, also flag `RECOVERY_REQUIRED` for human reconciliation; a matching claim alone is not proof that execution completed successfully.
   - If the record is missing, malformed, mismatched, or inconsistent with the ref history, return `BLOCKED` and request manual reconciliation.
5. If the ref does not exist, create one candidate claim commit directly on the exact PR HEAD. Do not reuse a dirty/stale local branch. Verify the parent and changed-path invariants.
6. Push only the deterministic claim ref using an ordinary non-force push. Never push the PR branch or stable branch as part of claiming.
7. Re-read the remote ref and record after the push:
   - Remote ref equals this candidate commit and `claim_attempt_id` matches this invocation: claim confirmed; return `CLAIMED`.
   - A valid matching run key exists but the attempt ID differs: another contender won; return `DUPLICATE_SKIP`.
   - Remote state is malformed or refers to another task/revision: `BLOCKED`.
   - Push outcome is ambiguous and remote state cannot yet be confirmed: `UNKNOWN`; do not start execution. Poll/read later for reconciliation; do not blindly create a new candidate.
8. If the server rejects a divergent push as non-fast-forward, re-read the winning ref. Only a valid matching record proves `DUPLICATE_SKIP`; otherwise return `BLOCKED`.

The Git server's ref-update checks provide a useful first-writer primitive for compliant contenders that create divergent commits from the same PR HEAD and push to the same deterministic ref. The PR #16 test verified a sequential divergent update was rejected. A truly simultaneous create-ref race has not yet been tested.

**MVP scope decision:** this release assumes one configured active WorkBuddy executor per queue, so simultaneous claims by multiple independent WorkBuddy executors are explicitly deferred and are not an MVP acceptance blocker. Keep the run key, claim record schema, state machine, and claim operation independent of executor count. If a future deployment enables multiple executors, concurrent-claim behavior must be tested before that topology is enabled; until then, do not claim that the Git ref is a proven distributed lock.

## 5. Execution state machine

Separate queue discovery results from durable execution states.

### Discovery/claim outcomes

- `NO_TASK`: no eligible opted-in PR exists.
- `TASK_FOUND`: eligible PR metadata has been identified; no execution permission is implied.
- `CLAIMED`: this invocation's claim ref and record were confirmed remotely.
- `DUPLICATE_SKIP`: a valid claim for the same run key already exists, or another contender won.
- `STALE`: the PR HEAD or eligibility changed during preflight.
- `BLOCKED`: permissions, policy, record validation, or required configuration failed.
- `UNKNOWN`: a remote write may have succeeded but cannot be confirmed. No execution is allowed.

### Execution states (future stage; disabled by default)

```text
UNSEEN
  -> VALIDATING
      -> NO_TASK
      -> BLOCKED
      -> STALE
      -> TASK_FOUND
          -> CLAIMING
              -> CLAIMED
              -> DUPLICATE_SKIP
              -> BLOCKED
              -> UNKNOWN
                  -> RECONCILING (read-only)
                      -> CLAIMED / DUPLICATE_SKIP / BLOCKED
              -> CLAIMED
                  -> RUNNING
                      -> REPORT_PENDING
                          -> COMPLETED
                          -> FAILED
                          -> BLOCKED
                      -> FAILED
                      -> BLOCKED
                      -> RECOVERY_REQUIRED
```

Terminal outcomes for a given run key are `COMPLETED`, `FAILED`, `BLOCKED`, `STALE`, and `RECOVERY_REQUIRED`. No automatic retry or reclaim is allowed after an ambiguous, failed, or abandoned run in this version. A retry requires explicit policy/owner approval and a separately recorded attempt; never delete or overwrite the original claim.

### Transition rules

| Current state | Allowed next state | Guard |
|---|---|---|
| `UNSEEN` | `VALIDATING` | Poller started with repository allowlist |
| `VALIDATING` | `NO_TASK` | No eligible PR |
| `VALIDATING` | `TASK_FOUND` | All discovery predicates pass |
| `VALIDATING` | `BLOCKED` / `STALE` | Policy/config/metadata failure or moving HEAD |
| `TASK_FOUND` | `CLAIMING` | Pre-claim re-read still matches |
| `CLAIMING` | `CLAIMED` | Remote ref and own attempt ID verified |
| `CLAIMING` | `DUPLICATE_SKIP` | Existing/winning valid claim matches run key |
| `CLAIMING` | `UNKNOWN` | Write outcome cannot be confirmed |
| `CLAIMING` | `BLOCKED` | Invalid record, permission error, or conflicting task |
| `UNKNOWN` | `RECONCILING` | Read-only remote inspection only |
| `RECONCILING` | `CLAIMED` / `DUPLICATE_SKIP` / `BLOCKED` | Determined from remote truth; never from assumption |
| `CLAIMED` | `RUNNING` | Only after a later stage is explicitly enabled and pre-execution SHA/policy checks pass |
| `RUNNING` | `REPORT_PENDING` | Approved command set completed and report assembled |
| `REPORT_PENDING` | `COMPLETED` | Evidence is committed and validated against tested SHA |
| `RUNNING` / `REPORT_PENDING` | `FAILED` / `BLOCKED` | Actual execution or policy failure |
| `RUNNING` | `RECOVERY_REQUIRED` | Timeout/crash/unknown side effects; human reconciliation required |

A poller must not turn `TASK_FOUND` directly into `RUNNING`. Claim verification and a separate execution authorization are mandatory.

## 6. Abandoned claims, stale SHA, and retry policy

- If the PR closes, becomes a draft, loses its opt-in label, changes base, or its HEAD changes before execution, do not execute. Mark the candidate stale/blocked in the run evidence; never transfer the old claim to the new SHA.
- If a worker crashes after claiming or the execution result is unknown, preserve the claim and require manual reconciliation. Do not infer that a timeout means the command did not run.
- This version has no automatic lease expiration or claim stealing. Expiring a claim based only on wall-clock time can create two executors if the original worker is merely slow/offline.
- A retry after a terminal failure requires an explicit owner-approved retry policy and a distinct attempt identity with auditable linkage to the original run. Never reset the original claim in place.
- The claim ref and all audit records are retained until a separately approved cleanup procedure exists.

## 7. Execution authorization and safe command boundary

Even a valid claim does not authorize arbitrary code execution.

Before execution is enabled for any repository, its project config must explicitly define:

- allowed repository and stable base branch;
- approved build/test commands and working directory;
- permitted file/system/network scope and timeout;
- expected report path and required evidence;
- whether any write-back is allowed (default: report-only);
- deployment policy (default: `DISABLED`);
- recovery/rollback and human approval requirements.

Commands must come from reviewed project configuration or the approved task contract, not be blindly copied from PR comments, filenames, or untrusted repository text. Fork PRs, arbitrary shell requests, secret exfiltration, force pushes, direct stable-branch writes, merge/release/deploy, and destructive operations are prohibited by default.

Execution must verify the exact claimed effective source SHA before starting. A report must distinguish the tested source SHA, literal PR HEAD at poll time, and later report commit SHA; follow the V1.3 evidence contract; and never claim unrun checks passed. The command allowlist and safety policy must come from the trusted base branch, not from files being tested in the candidate PR.

## 8. Execution topology, extensibility, and known limits

- **MVP deployment profile:** configure one active WorkBuddy executor per queue and serialize overlapping runs within that executor. This is an operational default, not a permanent protocol invariant or a hard-coded limit on future implementations.
- Keep task identity (`run_key`), deterministic claim ref, claim-record schema, and state transitions independent of the number of executors. Do not include executor identity in the run key or claim ref, because that would allow different executors to create separate claims for the same task.
- Treat claim persistence/coordination as a replaceable implementation boundary. The MVP may use Git refs; a future implementation may provide another reviewed backend (for example, a GitHub API-backed store or an atomic coordination service) without changing the task identity and state-machine contract.
- An optional `executor_id` may be recorded for diagnostics and audit, but it must not alter task identity or allow a second executor to bypass an existing claim.
- All writers must use the same deterministic ref and must never force-push. Initial claim commits must be based on the exact PR HEAD; after a rejected or ambiguous push, read and validate remote state before deciding the outcome.
- The PR #16 experiment tested sequential duplicate reads and a sequential divergent non-fast-forward rejection only. It did not test simultaneous workers, crashes during push, protected-ref policy, or hostile writers sharing credentials.
- **Deferred:** simultaneous first-claim races between multiple WorkBuddy executors are not required to accept the single-executor MVP. Before multi-executor mode is enabled in a later version, add and pass concurrent-claim tests; if Git ref behavior is insufficient, use a separately reviewed atomic coordination mechanism.
- GitHub branch refs plus shared SSH credentials are an audit/coordination mechanism, not a cryptographic authorization boundary against compromised workers sharing those credentials.

## 9. Required observability

Every attempt report must include:

- repository, PR, base branch, literal PR HEAD SHA, effective source SHA and deterministic run key;
- claim ref, candidate claim commit SHA, remote ref SHA, and claim attempt ID;
- state transitions with UTC timestamps (append-only; do not mutate earlier events);
- actual Git operations and exit codes, with secrets redacted;
- whether the result was `CLAIMED`, `DUPLICATE_SKIP`, `STALE`, `BLOCKED`, or `UNKNOWN`;
- if execution was authorized: exact command, environment, exit code, tested SHA, report commit SHA and evidence links;
- any uncertainty, stale state, rejected push, or manual recovery required.

## 10. Implementation gate

This is a design document, not permission to execute. Do not enable unattended build/test until:

1. the protocol and acceptance matrix are reviewed and approved;
2. the single-executor MVP profile and single-flight behavior are validated; multi-executor race tests are explicitly deferred and are not an MVP gate;
3. ambiguous push outcomes, stale SHA, invalid records, missing permissions, and abandoned execution are covered;
4. the executor uses an explicit repository/command allowlist and a single-flight guard;
5. report-only write-back is verified against the V1.3 evidence gate;
6. a user explicitly authorizes the first harmless command execution.

Before a later deployment enables multiple WorkBuddy executors, concurrent-claim tests and any required stronger coordination must be completed. This future requirement must remain an extension gate, not a restriction baked into the protocol or data model.

No merge, release, or deployment is authorized by this document.

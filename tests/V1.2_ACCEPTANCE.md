# V1.2 Acceptance — optional GitHub-native PR notifications

## Tested scope and safety boundary

The root AGENTS.md must still work alone (V1.1 manual PR handoff).
The optional workflow consists of .github/workflows/ai-dev-bridge-notify.yml
and .github/scripts/bridge_notify.py. It uses pull_request rather than
pull_request_target, skips fork/draft PRs, and cannot wake either AI.

A GitHub bot comment is **notification-only evidence**. It is never evidence
that WorkBuddy ran tests or that ChatGPT reviewed a report.

## ChatGPT preflight (do not fake execution results)

1. Verify the PR description contains one [AI_DEV_BRIDGE_HANDOFF] block.
2. Verify the workflow is limited to pull_request and same-repo non-draft PRs.
3. Verify the Python script does not execute PR body content or checkout fork
   code with privileged tokens, and that no long-term secret is required.
4. Verify that source/config changes are classified CODE_READY, while only
   added immutable report files cause REVIEW_PENDING.
5. Verify the V1.1 AGENTS.md single-file manual workflow is still supported.
6. Look up actual GitHub Actions runs for the PR; do not assume that
   adding a workflow file automatically produces a successful notification.

## WorkBuddy real environment run

- Use the PR link to get the **latest full 40-character SHA**, check it out.
- Record OS, Python version, Git version, exact commands and exit codes.
- Run the offline tests without installing external dependencies:

~~~sh
python3 -m unittest discover -s tests -p 'test_bridge_notify.py' -v
python3 -m py_compile .github/scripts/bridge_notify.py
git rev-parse HEAD
~~~

If python3 is not available but an authorized Python 3 interpreter is
available as python or py -3, state the actual command used. Do not
install Python without permission.

- An optional dry-run can be performed with a synthetic PR event JSON,
  set GITHUB_EVENT_PATH and GITHUB_REPOSITORY, and run
  python3 .github/scripts/bridge_notify.py --dry-run.
  A dry run does NOT post to GitHub or imply bot permissions.
- If all actual offline tests pass, report Tests: PASS for the offline suite.
- GitHub Actions integration delivery must be checked separately;
  no bot comment = NOT VERIFIED / BLOCKED rather than PASS.

## GitHub Actions actual notification acceptance

1. For an eligible same-repo, non-draft PR with the handoff block, an actual
   Actions job should run and, when token rights permit, add a CODE_READY
   comment containing the latest full HEAD SHA.
2. A new commit that adds only a correctly named, numbered WorkBuddy report
   should produce a REVIEW_PENDING bot comment, **not an automatic test PASS**.
3. If GitHub does not trigger the workflow, lacks issues:write or GitHub API
   access, record SKIPPED/BLOCKED with the actual Actions run/log or response.
4. A repeated event for the same SHA/kind must not produce a duplicate comment.
5. Mixed code + report changes must not be classified report-only.
6. Draft/fork PRs must not receive write-token-driven notifications.
7. Do not merge main or deploy before user approval.

Save an immutable sanitized report as a PR comment or under
.ai-collab/reports/PR-<PR>-<tested7>-a1.md in the same PR branch.
Never overwrite a previous report; preserve the tested commit and the
later report commit SHA separately. ChatGPT must verify with GitHub compare.

## Release gate

Offline tests alone prove only classifier behavior. Before calling the
GitHub-native notification feature truly operational, separately verify
the actual Actions run and bot comments and make sure no secrets or
unexpected file changes were pushed. The user decides whether to merge
V1.2 and create any Release or tag.
